# Antivirus Lab

## Description

A Bash-based antivirus daemon that monitors a directory for changes, detects suspicious files, and moves them to a quarantine directory.

The project also includes a restore utility that allows users to review quarantined files, restore falsely flagged files, or permanently delete them.

The project includes an additional Cron-based scanning script that performs a single scan each time it is executed. Cron is responsible for scheduling repeated executions.


### Main Files and Directories

- `antivirusd.sh`: Monitors the source directory, detects changes, scans files, and quarantines suspicious files.
- `antivirus-cron.sh`: Performs a single scan of the monitored directory and quarantines suspicious files. It is intended to be executed periodically by Cron.
- `restore.sh`: Lists quarantined files and allows users to restore or permanently delete them.
- `test.sh`: Used for testing file detection.
- `Makefile`: Provides targets for creating the quarantine directory and running the scripts.
- `README.md`: Documents the project and explains how to use it.
- `monitored/`: Directory monitored by the antivirus daemon.
- `malicious_dir/`: Directory where suspicious files are quarantined.
- `directory-info.last`: Stores the previous directory snapshot used by the daemon.
- `directory-info.new`: Stores the latest directory snapshot used to detect changes.
- `cron.log`: Stores the output and errors generated by scheduled Cron executions.

The snapshot files are generated by the daemon and may not exist before the first run. The `cron.log` file is created when the Cron job first writes output to it.

## Setup

Navigate to the project directory:

```bash
cd ~/Desktop/OS/Lab2
```

Replace this path with the actual project directory if it is stored elsewhere.

Make the scripts executable:

```bash
chmod +x antivirusd.sh antivirus-cron.sh restore.sh test.sh
```

Create the quarantine directory using the Makefile:

```bash
make
```

This creates `malicious_dir/` if it does not already exist.

Ensure that the source directory `monitored/` exists before running the scripts.

## Running the Antivirus Daemon

Run the daemon using:

```bash
make daemon
```

The daemon performs an initial scan when it starts, then checks the monitored directory every five seconds.

To run it directly with custom arguments:

```bash
./antivirusd.sh monitored/ malicious_dir/ 5
```

The arguments are:

1. `monitored/`: Source directory to monitor.
2. `malicious_dir/`: Destination directory for quarantined files.
3. `5`: Interval in seconds between checks.

Press `Ctrl+C` to stop the daemon.

## Detection Rules

The required detection rules are defined inside the `scan_directory()` function in `antivirusd.sh`.

### Flagged Extensions

The extension list is defined in the `case` statement:

- `.exe`
- `.bat`
- `.vbs`
- `.scr`
- `.ps1`

### Flagged Keywords

The keyword list is defined in the `grep -qiE` command:

- `virus`
- `trojan`
- `malware`
- `worm`
- `ransomware`

Keyword matching is case-insensitive.

A file is considered suspicious if its extension matches one of the flagged extensions or its contents contain one of the flagged keywords.

When a suspicious file is detected, the script copies it into `malicious_dir/` and deletes the original from `monitored/` after a successful copy.

The scripts scan files directly inside the monitored directory and do not recursively scan nested directories.

## Restoring Quarantined Files

Run:

```bash
make restore
```

Alternatively, run the restore script directly:

```bash
./restore.sh monitored/ malicious_dir/
```

The script lists the files in the quarantine directory and allows the user to choose a file and one of the following actions:

1. Restore the file to the monitored directory.
2. Permanently delete the file from quarantine.
3. Leave the file unchanged and return to the file list.

If the quarantine directory is empty when the tool starts, it displays:

```text
No malicious files to review.
```

Restored files may be detected and quarantined again if they still match a detection rule, unless a whitelist feature has been implemented.

## Bonus 1: Cron Scheduling

The project includes `antivirus-cron.sh`, which performs one scan of the monitored directory each time it is executed.

Unlike `antivirusd.sh`, the Cron script does not run an infinite monitoring loop. Cron is responsible for scheduling repeated executions.

### Manual Cron Setup

#### 1. Make the script executable

```bash
chmod +x antivirus-cron.sh
```

#### 2. Find the absolute project path

Navigate to the project directory and run:

```bash
pwd
```

For example, the project path might be:

```text
/home/ziad/OS/Lab2
```

Use the actual absolute path on your machine in the Cron configuration.

#### 3. Open the user's Cron table

```bash
crontab -e
```

#### 4. Add the scheduled task

The following entry runs the scanning script every minute, waits approximately 23 seconds, and writes the script's output and errors to `cron.log`.

Replace the example paths if your project is stored elsewhere.

```cron
* * * * * sleep 23; /home/ziad/OS/Lab2/antivirus-cron.sh /home/ziad/OS/Lab2/monitored /home/ziad/OS/Lab2/malicious_dir >> /home/ziad/OS/Lab2/cron.log 2>&1
```

The Cron fields are:

```text
minute hour day-of-month month day-of-week
```

The expression `* * * * *` means the task is scheduled every minute.

The command `sleep 23` delays the script execution by approximately 23 seconds after Cron starts the command.

**Important:** Traditional Cron schedules jobs by the minute and does not provide native second-level scheduling. The `sleep 23` approach is a workaround, not a guarantee that the script will start at exactly second 23.

If a scan takes longer than a minute, a subsequent scheduled invocation may start before the previous invocation finishes.

#### 5. Save and verify the Cron entry

Save the file and exit the editor.

List the scheduled tasks:

```bash
crontab -l
```

The Cron entry should appear in the output.

#### 6. Verify the Cron service

Check that the Cron service is running:

```bash
systemctl status cron
```

If necessary, enable and start it:

```bash
sudo systemctl enable --now cron
```

### Testing and Logs

Create a test file containing a suspicious keyword:

```bash
echo "This file contains a virus" > monitored/cron_test.txt
```

Wait for the next scheduled scan.

Check the quarantine directory:

```bash
ls malicious_dir/
```

Check whether the original file remains in the monitored directory:

```bash
ls monitored/
```

Inspect the Cron execution log:

```bash
cat cron.log
```

A successful detection should produce output similar to:

```text
Monitored directory: /home/ziad/OS/Lab2/monitored
Quarantine directory: /home/ziad/OS/Lab2/malicious_dir
cron_test.txt is malicious and it is DELETED
```

After successful detection, the test file should be present in `malicious_dir/` and absent from `monitored/`.

The log records output and errors from the scheduled command because the Cron entry redirects standard output and standard error to `cron.log`.

Only use disposable test files when testing, because detected files are removed from the monitored directory after successful copying.

### Scheduling the Third Friday of Each Month at 12:31 AM

A standard Cron expression has five scheduling fields:

```text
minute hour day-of-month month day-of-week
```

The intended schedule is the third Friday of every month at 12:31 AM.

A simple expression such as:

```cron
31 0 15-21 * 5
```

should not be assumed to mean the third Friday on traditional Cron implementations. When both the day-of-month and day-of-week fields are restricted, standard Cron implementations commonly treat them as alternative matching conditions rather than requiring both to match.

A robust approach is to schedule a wrapper script every Friday at 12:31 AM and have that wrapper check whether the day of the month is between 15 and 21 before running the intended task.

The wrapper's Cron entry would be:

```cron
31 0 * * 5 /absolute/path/to/third-friday-wrapper.sh
```

The wrapper must verify that the current day of the month is between 15 and 21. Since the third Friday always falls between the 15th and the 21st, this additional check ensures that the task runs only on the third Friday.

Replace `/absolute/path/to/third-friday-wrapper.sh` with the actual absolute path to the wrapper script.

**Note:** This third-Friday example describes the scheduling approach. The wrapper script must be created and tested separately before this schedule can be considered implemented.

## Important Notes

- The monitored directory should contain files directly, without nested subdirectories.
- The daemon and restore utility should not run concurrently.
- Restored files may be detected again by the daemon if they still match a detection rule, unless a whitelist feature has been implemented.
- Cron scheduling is implemented through `antivirus-cron.sh` and the user's Cron table.
- The Cron job uses absolute paths because Cron may run commands from a different working directory.
- The third-Friday schedule requires a wrapper script that checks the date; the example Cron entry alone is not sufficient.
- The whitelist feature is optional and should only be considered implemented if it has actually been completed.
